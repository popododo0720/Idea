## 흐름

```
사람: 이슈 작성
  │  웹훅 (HMAC-SHA256 서명 검증)
  ▼
컨트롤러 ── Task 생성 (이슈당 하나: 이름 고정 + Postgres 유일 키)
  │ Pending ─▶ WorkerStarting   작업 VM(Kata 포드) 생성
  │         ─▶ Working          메인 에이전트 Job 시작 → worker_run으로 작업 VM에 위임
  │                             작업 VM: 클론 → 브랜치 → 구현·테스트 → push → PR
  │         ─▶ Gate             PR의 테스트 결과를 기다림 (Forgejo Actions, Kata 러너)
  │         ─▶ Done             통과: 머지, 이슈에 댓글, 작업 VM 정리
  └         ─▶ Failed           실패: 머지 안 함, 이슈에 댓글, 작업 VM 정리
```

## 구성

### 플랫폼 (`deploy/platform/`, 네임스페이스 `idea-system`)

- **PostgreSQL 18.6**: 공식 이미지의 StatefulSet 하나. 데이터베이스와 역할은 소비자별로 따로(`forgejo`, `idea`).
- **Forgejo 15.0.11**: 공식 Helm 차트(HelmRelease). SSH 끔, 가입 끔, Actions 켬.
- **경로 `/git/`**: Forgejo는 URL 접두사를 스스로 처리하지 않고 Cilium Ingress는 경로를 고쳐 쓰지 못한다. 접두사를 떼어 주는 작은 nginx(`forgejo-subpath`)를 앞에 뒀다. 클러스터 안의 포드는 `http://forgejo-http:3000/`으로 직접 붙는다.
- **영구 볼륨**: Local Path Provisioner. VM의 둘째 디스크(`/dev/vdb`)를 Talos 사용자 볼륨으로 잡아 그 위에 둔다.
- **비밀번호**: Postgres 3개, Forgejo 관리자, 웹훅 시크릿 모두 External Secrets Operator의 `Password` 생성기가 클러스터 안에서 한 번 만든다.

### 컨트롤러 (`controller/`, Go)

- 고루프 3개: Forgejo 상태 맞추기(30초), 열린 이슈 훑기(60초, 웹훅을 놓쳤을 때 대비), Task 진행(5초).
- **Forgejo 안의 상태를 선언대로 유지한다**: 조직 `idea`, 저장소 `hello-calc`(비어 있으면 `examples/hello-calc`로 채움), 작업용 계정 `idea-worker`와 토큰, 웹훅, Actions 러너 등록 토큰. 지워지면 다시 만든다.
- **작업용 토큰의 범위**: 관리자가 아닌 별도 계정 `idea-worker`를 만들고 그 저장소의 협업자(쓰기)로만 넣었다. Forgejo 토큰은 저장소 단위로 좁힐 수 없어서, 계정 자체가 그 저장소에만 접근하게 했다.
- **Task의 상태는 Task 리소스의 `status` 하나가 기준이다.** Postgres에는 "이슈당 하나" 보장(`tasks` 유일 키)과 이력(`task_events`)만 둔다. 메모리에만 있는 상태는 없다.
- 각 단계는 "지금 클러스터에 무엇이 있는가"에서 할 일을 다시 계산하므로 몇 번을 반복하거나 중간에 죽어도 된다.
- 완료 판정은 에이전트의 말이 아니라 사실로 한다: PR이 실제로 있는가, 커밋 상태가 `success`인가.

### 테스트 관문: Forgejo Actions

- **Forgejo Actions가 됐다.** 대체안(컨트롤러가 직접 테스트)은 쓰지 않았다. 코드는 남겨 두었고 `GATE_MODE=controller`로 켤 수 있다(실행해 보지는 않았다).
- 러너(`deploy/apps/runner/`)는 작업 네임스페이스의 **Kata 포드**다. PR의 테스트는 신뢰할 수 없는 코드라서 작업 VM과 같은 네트워크 정책을 받는다.
- 실행 방식은 host 실행기(러너 포드 안에서 직접 실행)다. Docker가 필요 없다.
- 워크플로(`examples/hello-calc/.forgejo/workflows/test.yml`)는 저장소를 클러스터 안 주소로 직접 클론한다. 러너가 Forgejo의 공개 주소(`https://idea.internal/git/`)에 닿을 수 없기 때문이다.

## 막힌 점과 해결

- **Forgejo가 `/git/` 접두사를 받지 않는다**(404). 위의 nginx 프록시로 해결.
- **Forgejo 포드가 Pod Security `restricted`에 걸렸다.** 차트 값으로 보안 컨텍스트를 줬다.
- **이름 충돌**: 우리 Ingress 이름이 Helm 릴리스가 만들던 Ingress와 같아서, 릴리스 업그레이드가 우리 것을 지웠다. 이름을 바꿨다.
- **Flux 상태 확인이 오래 붙잡힌다**: `wait: true`인 계층은 앞 리비전의 상태 확인(최대 15분)이 끝나야 다음 리비전을 적용한다. 잘못된 리비전을 올리면 고친 것을 올려도 그만큼 기다린다.
- **재구축 때 etcd 시간 초과**: 큰 이미지를 받는 동안 디스크가 밀려 etcd 쓰기가 한 번 시간 초과됐고, Flux 루트 계층의 상태 표시가 다음 주기(10분)까지 "진행 중"으로 남았다. 실제 리소스는 떠 있었고 스스로 회복했다. 수렴 시간 27분 중 약 10분이 이 대기다.
- **영구 볼륨이 없었다.** Talos 단일 노드에는 StorageClass가 없어서 둘째 디스크 + 사용자 볼륨 + Local Path Provisioner를 넣었다.

## 계획과 다르게 한 것

- **Postgres는 HelmRelease가 아니라 StatefulSet 매니페스트다.** 널리 쓰이던 차트의 이미지 배포 정책이 바뀐 상황이라, 공식 이미지를 직접 쓰는 쪽이 의존이 적다. Forgejo는 계획대로 HelmRelease다.
- **컨트롤러용 Helm 차트(`charts/`)는 만들지 않았다.** 매니페스트를 `deploy/apps/controller/`에 그대로 뒀다.
- **Forgejo 상태의 선언은 CRD가 아니라 컨트롤러 설정(환경 변수)이다**: 조직과 저장소 이름 하나씩. 저장소가 여러 개가 되면 CRD나 설정 파일로 바꿔야 한다.
- **Postgres, Forgejo, 컨트롤러, 메인을 한 네임스페이스(`idea-system`)에 뒀다.** 생성한 비밀번호를 네임스페이스 사이로 옮기는 장치를 줄이기 위해서다. 신뢰 경계는 `idea-system`(신뢰)과 `idea-work`(비신뢰) 둘이다.
- **작업용 토큰은 "저장소 범위 토큰"이 아니라 "그 저장소에만 권한이 있는 계정의 토큰"이다**(위 참고).

## 운영하면서 지킨 것, 어긴 것

- 클러스터 안의 것은 전부 `deploy/`의 선언이고 Flux가 맞췄다. 손으로 만든 리소스는 시험용뿐이었고 지웠다.
- **어긴 것 1건**: Forgejo API를 확인하면서 관리자 비밀번호를 명령줄 인자(`kubectl exec … env FJ_PASS=…`)로 한 번 넘겼다. 4.6의 "명령줄 인자로 시크릿을 넘기지 않는다"를 어긴 것이다. 그 값은 이 호스트의 프로세스 목록에 몇 초 보였을 뿐 레포·로그·이미지에는 들어가지 않았고, 그 뒤 VM을 재구축해 그 비밀번호는 더 이상 쓰이지 않는다. 이후로는 표준 입력으로 넘기는 `scripts/forgejo-api.sh`를 만들어 썼다.

## 설계에 반영할 점

- **리뷰 관문(Kodus) 자리**: `Gate` 단계가 "커밋 상태가 `success`인가"만 본다. 리뷰 도구가 커밋 상태를 하나 더 달면 코드 변경 없이 관문이 된다(Forgejo의 합산 상태는 모든 상태가 통과해야 `success`다). 인터페이스는 이것으로 충분하다.
- **메인 에이전트의 역할이 얇다.** 지금 메인은 "worker_run을 한 번 부르고 요약"만 한다. 컨트롤러가 SSH로 직접 맡겨도 결과는 같다. 메인을 두는 가치는 과제를 나누거나 여러 작업 VM을 조율할 때 생긴다.
- **실패한 Task는 다시 시도하지 않는다.** 이슈는 열린 채로 남고 Task는 `Failed`다. 재시도 방법(댓글 명령, Task 삭제)을 정해야 한다.
- **작업 VM은 Task가 끝나면 지운다.** 실패 원인을 보려면 지우기 전에 세션 기록을 어딘가로 옮겨야 한다. 지금은 Postgres에 단계 이력만 남는다.
- **러너가 재시작할 때마다 새로 등록한다.** 오래 쓰면 Forgejo에 죽은 러너 항목이 쌓인다. 러너도 host 실행기라 실행 사이에 파일이 남을 수 있다(완전히 깨끗한 환경은 아니다). 일회용 러너로 바꾸는 것을 검토한다.
- **워크플로 파일에 클러스터 안 주소가 들어 있다.** 사용자의 저장소에 그런 것을 요구할 수는 없다. 러너가 공개 주소로 Forgejo에 닿게 하거나(인그레스 경유 허용 + 인증서 신뢰), 체크아웃 액션의 주소를 바꿔 주는 설정이 필요하다.
- **웹훅 시크릿을 바꾸면 기존 웹훅은 옛 시크릿을 그대로 쓴다.** 컨트롤러는 주소만 비교한다. 시크릿이 바뀌면 웹훅을 지웠다 다시 만들어야 한다.
- **etcd와 이미지 저장이 같은 HDD에 있으면 큰 이미지를 받을 때 etcd가 밀린다.** SSD에서는 문제가 안 될 가능성이 크지만, 작업 이미지(2.7GB)를 줄이거나 미리 받아 두는 것이 낫다.
- **Flux 계층의 `wait`와 긴 timeout**은 잘못된 리비전에서 복구를 늦춘다. `platform`, `apps`의 timeout을 줄이는 것을 검토한다.
- 모델 키는 여전히 작업 VM 안에 있다(단계 6의 메모와 같다).
